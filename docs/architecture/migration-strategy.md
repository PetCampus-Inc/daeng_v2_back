# 마이그레이션 전략

이 문서는 레거시 서버에서 신규 Kotlin/헥사고날 서버로 전환하는 현재 전략을 요약한다. 결정의 이력은 `docs/adr/`에 남기고, 이 문서는 최신 실행 기준을 유지한다.

## 1. 기본 방향

- 전체 시스템을 한 번에 재작성하지 않고, API/도메인 슬라이스 단위로 이관한다.
- 먼저 인벤토리와 정책 문서의 골격을 만들고, 작은 파일럿 슬라이스로 문서 기준이 실제 작업에 맞는지 검증한다.
- 프론트/앱이 의존하는 기존 계약은 유지하고, breaking change가 필요한 경우 `v1` 등 신규 API로 분리한다.
- 신규 DB는 레거시 스키마 복제가 아니라 도메인/API 슬라이스 단위로 Flyway migration을 쌓아 확정한다.

## 2. 문서 하네스

| 영역 | 기준 문서 |
|---|---|
| API 목록/판정 | `docs/api/inventory.md` |
| API 계약/버전 정책 | `docs/api/policy.md` |
| 데이터 객체 목록/판정 | `docs/database/inventory.md` |
| DB/Flyway/데이터 이관 정책 | `docs/database/policy.md` |
| 외부 연동 목록/판정 | `docs/integrations/inventory.md` |
| 운영 환경/전환 항목 | `docs/operations/inventory.md` |

## 3. 진행 순서

1. 기존 시스템의 API, 데이터, 외부 연동, 운영 항목을 인벤토리화한다.
2. 각 항목을 `KEEP`, `REDESIGN`, `DROP`, `DEFER`로 판정한다.
3. `KEEP` API의 계약 보존 기준과 parity 대상 여부를 정한다.
4. 작은 API/도메인 슬라이스 하나를 이관해 문서 기준과 구현 흐름을 검증한다.
5. 파일럿 결과를 문서에 반영하고, 다음 슬라이스를 같은 방식으로 진행한다.

## 4. 이번 문서 골격의 제외 범위

- 전체 API 명세 완성
- 전체 신규 DB 스키마 확정
- 전체 데이터 이관 스크립트 작성
- AWS IaC 구현
- 실제 컷오버/rollback 절차 확정
