# 작업 규칙

이 문서는 Jira 티켓을 받아서 머지까지 끝내는 전체 작업 절차를 정의한다. 특정 AI 도구나 플러그인에 의존하지 않는다 — 어떤 코딩 에이전트를 쓰든 이 절차를 그대로 따른다.

## 전체 흐름

| 단계 | 이름 | 산출물 |
|---|---|---|
| 1 | 티켓 수령 | - |
| 2 | 티켓 분석 | (사람과의 대화) |
| 3 | 본문 작성 + 브랜치 생성 | Jira 티켓 본문, 브랜치 |
| 4 | 구현 방향 논의 | (사람과의 대화) |
| 5 | 계획 문서 작성 | `docs/plans/<JIRA-KEY>-<kebab-설명>.md` |
| 6 | 구현 | 코드 |
| 7 | 커밋 | 커밋 (연관 작업 단위) |
| 8~9 | 리뷰 및 개선 | 리뷰 코멘트 반영 |
| 10 | PR 생성 | PR |
| 11 | PR 리뷰 및 수정 | 반영된 코드 |
| 12 | 문서 동기화 + 머지 | 최신화된 docs/*, 머지 |

## 1. 티켓 수령

Jira 티켓을 배정받는다. 이 시점에는 본문이 비어 있을 수 있다 — 티켓 제목/코멘트만으로 시작한다.

## 2. 티켓 분석

작업을 시작하기 전에 아래 세 가지를 반드시 파악한다. 이 분석 결과는 3번에서 티켓 본문에, 5번에서 계획 문서에 반영된다.

1. **배경/맥락**: 이 티켓이 왜 생겼는가. 관련 ADR(`docs/adr/`), 도메인 지시서(`docs/domains/`), 이전 대화/코멘트를 확인한다.
2. **작업 범위**: 생성/수정/삭제되어야 할 코드가 무엇인가. 파일·모듈 단위로 구체화한다.
3. **작업 후 확인 목록**: 완료 후 갱신해야 할 문서가 무엇인가. 작업 성격에 따라 다르다.

| 작업 성격 | 확인해야 할 문서 |
|---|---|
| 아키텍처/설계 변경 | `docs/adr/`, `docs/architecture/` |
| API 추가/변경 | Notion API 명세서 — 연동 방법은 [`docs/conventions/notion-api-spec-sync.md`](../conventions/notion-api-spec-sync.md) |
| 도메인 로직 변경 | `docs/domains/<domain>.md` |
| 이 문서들에 해당 없음 | 없음 — 생략 가능 |

불확실한 부분은 사람에게 직접 묻는다. 짐작하지 않는다.

## 3. 본문 작성 + 브랜치 생성

2번 분석이 끝나면:
1. Jira 티켓 본문을 채운다 (배경, 범위, 확인 목록 반영)
2. [`git.md`](git.md) 규칙에 따라 브랜치를 생성한다

## 4. 구현 방향 논의

2번에서 정한 범위를 실제로 어떻게 구현할지 논의한다. 여러 방법론 중 선택이 필요하거나 트레이드오프가 있는 지점을 짚는다. 결론이 아니라 "무엇을 검토했고 왜 배제했는지"까지 남긴다 — 이 논의 내용이 5번 문서의 근거가 된다.

## 5. 계획 문서 작성

4번 논의를 바탕으로 **하나의 문서**로 정리한다. 저장 위치: `docs/plans/<JIRA-KEY>-<kebab-설명>.md` (커밋 대상).

**필수 섹션 (이 순서, 이 이름 그대로):**

| 섹션 | 내용 |
|---|---|
| 작업 목표 | 이 티켓이 끝나면 무엇이 달성되는가 (1~2문장) |
| 작업 범위 | 생성/수정/삭제될 파일·모듈 (2번 분석 결과 반영) |
| 작업 제외 범위 | 이번에 하지 않는 것 — 왜 제외했는지 포함 |
| 방향 논의 및 결정 사항 | 4번에서 검토한 대안들과 최종 선택, 그 이유 |
| 완료 확인 기준 | 이 작업이 끝났다고 판단할 구체적 기준 (아래 참고) |
| 작업 후 확인 목록 | 2번 표에서 확인된, 갱신해야 할 문서 목록 |

**완료 확인 기준 작성 가이드**: 작업 성격에 맞는 검증 방법을 구체적으로 명시한다. 예:
- 헥사고날 경계를 다루는 백엔드 작업: ArchUnit 통과, ktlint 통과, (기존 응답을 유지해야 하면) 골든 테스트로 레거시와 응답 JSON 100% 일치 확인
- 그 외 작업: 테스트 명령어와 통과 기준을 명시

이 문서는 8번 리뷰 단계에서 컨텍스트 없는 리뷰어에게 그대로 전달된다. 리뷰어가 이 문서만 보고 "무엇을, 왜, 어디까지" 작업했는지 알 수 있어야 한다.

## 6. 구현

5번 문서를 기반으로 구현한다. 문서에 없는 범위로 확장하지 않는다(YAGNI). 계획과 다르게 가야 할 이유가 생기면, 코드를 먼저 바꾸지 말고 5번 문서를 먼저 갱신한다.

## 7. 커밋

연관된 작업 단위로 나누어 커밋한다. 커밋 메시지 형식은 [`git.md`](git.md)를 따른다. 하나의 커밋에 서로 무관한 변경을 섞지 않는다.

## 8. 리뷰

새로운 세션(컨텍스트를 공유하지 않는 리뷰어)에게 리뷰를 맡긴다. 리뷰어에게 반드시 전달할 것:
- 5번 계획 문서 경로 — "요구사항과 배경은 이 문서를 읽어라"
- 리뷰 대상 커밋 범위 (base/head)

리뷰어는 계획 문서와 실제 diff를 대조해 다음을 확인한다: 계획에 있는데 빠진 것, 계획에 없는데 추가된 것, 계획과 다르게 구현된 것. 필요하면 리뷰어가 직접 코드베이스를 더 탐색할 수 있어야 한다.

## 9. 개선 반복

리뷰에서 나온 문제를 수정하고, 더 이상 고칠 부분이 없다고 판단될 때까지 8~9번을 반복한다. 리뷰가 지적한 문제를 "이번 범위 아님"으로 넘기려면, 5번 문서의 "작업 제외 범위"에 이유와 함께 명시적으로 추가한다.

## 10. PR 생성

[`git.md`](git.md)의 PR 본문 템플릿을 따른다. 5번 계획 문서의 "작업 목표"/"작업 범위"를 PR의 Summary/Notes에 반영한다.

## 11. PR 리뷰 및 수정

사람 리뷰어와 AI 리뷰 도구의 코멘트를 반영한다. 반영 후에도 8~9번과 동일하게, 남겨두기로 한 지적은 이유와 함께 기록한다(PR 코멘트 답글 또는 5번 문서 갱신).

## 12. 문서 동기화 + 머지

머지 직전, 최종 PR 내용을 기준으로 아래를 갱신한다:
- 5번 문서의 "작업 후 확인 목록"에 있는 문서들 (`docs/adr/`, `docs/domains/*.md` 등)
- API를 추가/변경했다면 [`docs/conventions/notion-api-spec-sync.md`](../conventions/notion-api-spec-sync.md) 규칙에 따라 Notion API 명세서 페이지를 생성/수정
- PR 본문이 최종 코드와 어긋나 있으면 함께 갱신

문서 갱신까지 끝난 뒤에만 머지한다. "머지 후 문서화"는 하지 않는다 — 머지 시점의 코드와 문서가 항상 일치해야 한다.
