# 데이터베이스 정책

이 문서는 신규 서버의 DB 스키마 변경, 데이터 이관, 검증 원칙을 정의한다. 실제 데이터 객체별 판정은 `docs/database/inventory.md`에서 관리한다.

## 1. 기본 원칙

- 신규 서버는 레거시 DB 스키마를 그대로 복제하지 않고, 신규 DB 인스턴스에 필요한 스키마를 새로 작성한다.
- 전체 스키마를 선행 확정하지 않고, 도메인/API 슬라이스 단위로 필요한 테이블과 제약을 확정한다.
- 스키마 변경은 Hibernate `ddl-auto: update`에 의존하지 않고 Flyway migration으로 남긴다.
- 데이터 이관 실행 시점은 후순위로 두되, 이관 대상·검증 기준·rollback 가능 여부는 데이터 객체별로 미리 기록한다.

## 2. Flyway 원칙

- 마이그레이션 파일은 `src/main/resources/db/migration/`에 둔다.
- 파일명은 `V<N>__<description>.sql` 형식을 따른다.
- 이미 공유된 migration 파일은 수정하지 않고 새 migration을 추가한다.
- Flyway가 단일 출처가 되는 시점에는 `FLYWAY_ENABLED=true`, `JPA_DDL_AUTO=validate` 전환을 검토한다.

## 3. 신규 스키마 확정 기준

신규 테이블은 아래가 확인된 뒤 추가한다.

| 항목 | 기준 |
|---|---|
| 사용 유스케이스 | 어떤 API/도메인 흐름에서 필요한지 명시 |
| 소유 도메인 | 데이터를 생성·변경할 도메인 명시 |
| 제약 | unique, FK, nullable, 상태값, 삭제 정책 명시 |
| 인덱스 | 조회 패턴 근거가 있는 인덱스만 추가 |
| 이관 | legacy source, 변환 규칙, 검증 기준 명시 |

## 4. 데이터 검증 기준

- 단순 이관 데이터는 row count를 비교한다.
- 변환이 있는 데이터는 샘플 비교 또는 checksum 기준을 추가한다.
- 삭제/미이관 데이터는 보존 의무와 폐기 근거를 남긴다.
- rollback이 불가능하거나 비용이 큰 변경은 작업 전에 별도 계획 문서에 명시한다.
