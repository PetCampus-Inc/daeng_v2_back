# 0007. 인가 정책: 기본 permit → 기본 deny로 전환

## 맥락

현재 서버의 인가 정책은 `anyRequest().permitAll()` 뒤에 `@PrivateAccess`가 붙은 엔드포인트만 `authenticated()`로 요구하는 구조다 — 기본값이 "공개"이고, 개발자가 어노테이션을 빠뜨리면 그대로 인증 없이 뚫린다. 실제로 이 방식 때문에 여러 건의 인증 누락 사고가 발생했다([`0004-api-v0-유지-v1-신규.md`](0004-api-v0-유지-v1-신규.md) 부록 참고 — `PetController.updatePet`, `ComparisonController` 등).

## 검토한 후보

1. 기존처럼 기본 permit + `@PrivateAccess` 화이트리스트 방식을 유지한다.
2. 기본값을 뒤집어, 명시적 permit 목록(공개 API)만 화이트리스트로 선언하고 그 외 전부 인증을 기본으로 요구한다.

## 결정

**후보 2 — 기본 deny로 전환.**

근거: 어노테이션을 "빠뜨려서" 뚫리는 사고를 구조적으로 막는다. 새 엔드포인트를 추가할 때 실수로 공개돼버리는 대신, 실수로 막혀버리는 쪽이 안전하다(공개해야 할 걸 깜빡하면 즉시 404/403으로 드러나 발견하기 쉽다).

## 결과

- 신규 서버는 공개 API를 화이트리스트로 명시 선언하고, 그 외는 기본적으로 인증을 요구한다.
- `application.yml`의 `security.roles.*`(`ROLE_MEMBER`, `ROLE_OWNER` 등)는 실사용 0건(`SecurityRoleProperties` 참조처가 정의 클래스 자신뿐)인 죽은 설정이므로 이관하지 않는다.
- 세분화된 권한(원장 권한 등)은 Spring Security 역할이 아니라 각 도메인(`owner`)이 자체 테이블로 검증하는 현재 패턴을 유지한다 — 신규 서버에서 역할 기반 Spring Security를 새로 도입하지 않는다.
