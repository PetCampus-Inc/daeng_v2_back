# 0010. v3는 신규 DB 인스턴스에 스키마를 새로 작성, 데이터 이관은 최후순위로 미룸

## 맥락

[`0002`](0002-db-스키마-유지.md)에서는 언어/아키텍처 전환과 스키마 변경을 동시에 하지 않기 위해, 기존 운영 스키마를 그대로 쓰기로 했었다. 이후(2026-07-28) 리더와 논의한 결과, 방향이 바뀌었다 — DB 데이터 자체는 마이그레이션하되 그 시점을 최우선이 아니라 가장 나중으로 미루고, v3는 기존 DB를 공유하지 않는 새 DB 인스턴스에서 스키마를 처음부터 새로 작성하기로 했다.

## 검토한 후보

1. (기존 `0002`) 기존 운영 DB·스키마를 그대로 사용한다.
2. 신규 DB 인스턴스에 스키마를 새로 설계하고, 기존 데이터 이관은 별도 단계로 분리해 가장 마지막에 수행한다.

## 결정

**후보 2 — 신규 DB 인스턴스 + 신규 스키마.** 데이터 이관은 하되 가장 마지막 단계로 미룬다.

## 결과

- v3는 기존 DB와 별개인 새 DB 인스턴스에서, 스키마를 처음부터 새로 설계해 개발한다.
- 기존 데이터의 신규 DB 이관은 이번 스프린트 범위 밖 — 가장 마지막 단계로 미룬다.
- **재검토 필요**: 이 결정은 `0002`를 전제로 했던 다른 결정에 영향을 준다.
  - [`0008-무중단-컷오버-전략.md`](0008-무중단-컷오버-전략.md): "같은 DB를 그대로 쓰므로 롤백은 LB 전환만으로 무료"라는 전제가 깨졌다. 데이터 동기화/이관 전략을 포함해 컷오버 단계를 다시 설계해야 한다.
  - [`0004`](0004-api-v0-유지-v1-신규.md) 구현 메모(작업 단위 분해): 도메인 기반 태스크가 기존 스키마를 전제로 한 부분(JPA 엔티티 매핑 등)이 있다면 영향 범위를 재확인해야 한다.
