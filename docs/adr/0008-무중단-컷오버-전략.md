# 0008. 무중단 컷오버 전략 (4단계)

## 맥락

DB/Redis 스키마를 그대로 유지하기로 했으므로([`0002`](0002-db-스키마-유지.md)), 자바 서버에서 코틀린 서버로 전환하는 방식도 결정이 필요했다.

## 검토한 후보

1. 일괄 전환(빅뱅 컷오버) — 준비 완료 시점에 한 번에 트래픽을 옮긴다.
2. 단계적 컷오버 — 스키마 변경 없이 트래픽만 순차 전환하고, 안정화 기간을 두고서야 레거시를 폐기한다.

## 결정

**후보 2 — 단계적 컷오버.** 즉시 롤백이 가능해야 한다는 것이 최우선 조건이었다.

## 결과

```
1단계  Kotlin 서버가 기존 스키마·기존 Redis를 그대로 읽고 쓰도록 완성 (DB/Redis 변경 없음)
2단계  LB/도메인을 Kotlin 서버로 전환. 자바 서버는 트래픽만 내리고 유지(즉시 롤백 대비)
       단, blog-reviews 2개 경로는 레거시로 프록시 (0005)
3단계  1~2주 안정화 후 자바 서버 및 QueryDSL/MapStruct 등 잔존 의존성 폐기 (0006)
4단계  (후속 스프린트) DB 스키마 재설계, 크롤링 서비스 분리
```

같은 DB/Redis를 그대로 쓰기 때문에 2단계의 "롤백"은 LB를 자바 서버로 되돌리는 것만으로 끝난다 — 데이터 마이그레이션 롤백이 필요 없다.
