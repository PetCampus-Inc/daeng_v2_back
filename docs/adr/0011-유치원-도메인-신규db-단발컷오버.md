# 0011. 유치원 도메인: 신규 DB 단발 컷오버 + 유치원 정적 조회 `v1` 전면 전환

## 맥락

[`0010`](0010-신규-db-인스턴스-스키마-재작성.md)이 v3는 기존 DB와 별개인 신규 인스턴스에 스키마를 새로 쓰기로 결정하면서, [`0008`](0008-무중단-컷오버-전략.md)의 전제("같은 DB/Redis를 그대로 쓰므로 롤백은 LB 전환만으로 무료")가 깨졌다. 유치원 도메인(`daeng_v1_back` `kindergardeninfo` 패키지)을 조사한 결과, 레거시 조회 API의 실제 데이터 원본이 MySQL이 아니라 **Redis**(크롤링 JSON을 적재한 캐시)라는 것도 확인했다 — `KindergartenController`가 `RedisTemplate`을 직접 주입받아 조회하고, MySQL(`tb_school*`)은 원장이 인증해 수정한 프로필 오버라이드만 담당한다.

이 결정은 원래 별도 티켓(KD3-335, "v0 유치원 API 컷오버 전략 재설계")으로 분리했으나, 그 결론이 [KD3-413](../work/KD3-413-kindergarten-static-lookup.md)(유치원 정적 조회 이관)의 착수 조건 자체였기 때문에 KD3-413에서 직접 논의·확정했다.

## 검토한 후보

**컷오버 방식**

1. 레거시 Redis를 신규 서버도 그대로 공유해서 읽는다 — 인프라 분리가 안 되고, ADR 0010의 "신규 인스턴스" 취지와 어긋난다.
2. 레거시 API로 프록시한다(블로그 리뷰에 대한 [`0005`](0005-리뷰-크롤링-마이그레이션-보류.md)와 같은 패턴) — 신규 서버가 레거시에 계속 의존하게 되고, 레거시 폐기 시점(ADR 0008 3단계)이 묶인다.
3. 크롤링 JSON을 파싱해 신규 MySQL로 시딩하고, MySQL을 새 source of truth로 삼아 완전히 재구현한다 — 레거시와 인프라를 공유하지 않는다.

**API 계약** (구현 중 재논의 — 아래 "결정"이 최종안)

1. 레거시 이름(`main`, `basic` 등)을 그대로 두고 계약도 그대로 유지한다.
2. 이름이 실제 동작과 다른 경우([`api-migration.md`](../rules/api-migration.md) 기준)만 `v1`로 새로 이름 짓고, `v0`는 그 자리에서 폐기한다 — 프론트가 `v1`로 옮겨오기 전까지 클라이언트가 깨진다.
3. 이름이 실제 동작과 다른 경우만 `v1`로 새로 짓되, `v0`는 `v1` 구현 위에 얹은 프록시(어댑터)로 유지한다.
4. 이름이 같든 다르든 이번 3개 엔드포인트 전부 `v1`로 신규 추가한다. `v0`는 그대로 두되(레거시와 동일한 계약, 버그 포함), 새 서버가 계속 host할지 레거시로만 넘길지는 프론트 확인 후 결정한다.

## 결정

**컷오버는 후보 3 — 완전 분리 + 단발 전환.** 신규 서버·DB·Redis는 레거시와 인프라를 공유하지 않는다. 레거시와 트래픽을 공유하며 점진 전환하는 무중단 마이그레이션은 하지 않는다.

**API 계약은 후보 4 — 이름이 같든 다르든 이번 3개 엔드포인트 모두 `v1` 신규.** 애초엔 후보 3(이름이 다를 때만 `v1`)으로 시작했으나, 구현 중 "이번 기회에 유치원 정적 조회 전체를 `v1`으로 전면 전환한다"로 방향이 바뀌었다. `v0`는 삭제하지 않고 그대로 둔다(레거시와 동일 계약, 알려진 버그 포함) — 이 서버가 계속 응답할지, 레거시로만 라우팅될지는 이번 결정 범위가 아니다(프론트 확인 대기, 아래 참고).

**롤백 안전성은 별도로 설계하지 않는다.** ADR 0008이 최우선 조건으로 뒀던 "즉시 롤백 가능"을 이번 결정에서는 요구하지 않는다 — 롤백이 필요한 상황 자체를 낮게 본다.

## 결과

- 유치원 정적 조회(요약/상세/요금표)의 source of truth는 크롤링 JSON → 신규 MySQL이다. 레거시 Redis/MySQL은 더 이상 참조하지 않는다.
- 유치원 식별자는 네이버 지도 `placeId` 기준. 원장이 자체 등록(네이버 미등재)하는 유치원은 레거시 `manual_` 접두사 관례를 계승해 별도 발급 ID를 부여한다.
- `GET /api/v1/kindergartens/{id}/summary`, `/detail`, `/pricing`을 신규 추가한다. `summary`/`detail`은 레거시(`main`/`basic`)에서 발견한 버그 2개를 고쳤다 — `address`/`roadAddress` 분리, `operationStatus`에 `HOLIDAY` 구분 추가. `detail`에서는 실체 없는 `breakTime` 필드도 뺐다. 상세는 `docs/domains/kindergarten.md` §2 참고.
- `GET /api/v0/kindergarten/main/{id}`, `basic/{id}`, `{id}/pricing`(레거시와 동일 계약, 버그 포함)도 이 서버에 남겨둔다. 이 서버가 `v0`를 계속 host할지는 프론트 확인 후 결정한다 — **미결**.
- **`v0`=`v1` 프록시 패턴(원안)은 이번엔 적용하지 않는다.** `api-migration.md`가 그린 프록시 어댑터는 `v0`와 `v1`이 같은 데이터를 담고 형태만 다를 때 성립하는데, 이번엔 `v1`이 버그를 고쳐서 `v0`와 내용 자체가 다르다(휴무일에 `v0`는 `CLOSED`, `v1`은 `HOLIDAY` 등) — `v0`가 `v1` 위에 얇게 얹히면 `v0`도 고쳐진 값을 돌려주게 돼 계약을 못 지킨다. 그래서 `v0`/`v1` 컨트롤러는 같은 조회 유스케이스 위에 각자 독립된 응답 매핑을 갖는다(코드 중복은 있지만 계약이 갈리는 이상 불가피).
- `GET /api/v0/kindergarten/filters/result`(개수 반환인데 이름이 `result`)는 [`0004`](0004-api-v0-유지-v1-신규.md)가 이미 정한 `v1` 신규 원칙의 적용 대상이나, 아직 착수하지 않았다(map-view 계열 후속 작업).
- `map-view`/`near`/`autocomplete`/`filters/result` 등 지도·좌표 기반 동적 조회는 이 결정의 적용 범위이나 구체 아키텍처(Redis 캐시 여부 등)는 후속 하위 작업에서 별도로 정한다.
- 데이터 이관(레거시 운영 DB→신규 DB의 실데이터 이관)은 [`0010`](0010-신규-db-인스턴스-스키마-재작성.md)에 따라 계속 최후순위다. 이번 결정은 크롤링 JSON 재파싱 시딩이지 운영 데이터 이관이 아니다.
