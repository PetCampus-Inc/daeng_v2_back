# 0004. API 경로: `v0` 유지 + RESTful 신규는 `v1`로 추가

## 맥락

Java → Kotlin 마이그레이션 시점에 API 경로 체계도 같이 손볼지 결정이 필요했다. 프론트(`daeng_v2_front`)와 모바일 앱은 기존 `v0` 경로를 그대로 호출하고 있다.

## 검토한 후보

1. 마이그레이션과 동시에 모든 API를 RESTful `v1`로 일괄 전환한다 — 프론트/앱 동시 수정 필요.
2. 기존 `/api/v0/**`는 그대로 유지하고, RESTful하게 재설계할 것만 `/api/v1/**`로 신규 추가한다. 프론트 전환이 끝나면 `v0`를 삭제한다.

## 결정

**후보 2 — `v0` 유지 + `v1` 신규 추가 (사용자 확정 사항).**

근거: 프론트 코드 수정 없이 백엔드 컷오버가 가능하다. 프론트가 `v1`로 넘어온 뒤에야 `v0`를 지운다.

### 부록: 함께 발견된 보안 이슈 (마이그레이션과 별개 — 자바 서버 우선 패치 권장)

프론트 코드 대조로 확정된 실사용 취약점. 이번 스프린트 범위 밖이지만 방치 리스크가 커서 기록해둔다. 사용자 확인: 이번 스프린트에서는 자바 서버를 별도로 건드리지 않기로 함 — 리스크로만 기록.

| 문제 | 위치 | 영향 |
|---|---|---|
| 인증 없이 타인 정보 수정 가능 | `PetController.updatePet` (`POST /pet/update/{petId}`) | 다른 pet API 4개는 모두 `@PrivateAccess`인데 이것만 누락. petId만 알면 누구나 수정 가능. 프론트 실사용 확인됨 |
| 인증 없이 업로드 URL 발급 | `S3ImageUploadController.getUploadPreSignedUrl` | 누구나 자신 명의로 S3 업로드 가능한 pre-signed URL 발급 |
| `@PrivateAccess`가 permit 규칙에 가려짐 | `ComparisonController` (`/api/v0/kindergarten/comparisons/history*`) | `security.permit-urls`에 `/api/v0/kindergarten/**`가 있어 먼저 매칭 → 개인 비교 히스토리 조회/삭제가 인증 없이 열림. 프론트 실사용 확인됨 |
| 배포마다 전체 로그아웃 | `KindergartenRedisLoader.loadJsonToRedis` (`@EventListener(ApplicationReadyEvent)`) | 무조건 `redisTemplate...flushDb()` 호출 → 같은 Redis DB의 `RedisRefreshToken` 전량 삭제. 신규 서버 쪽 대응은 아래 구현 메모 참고 |
| 운영에 노출된 위험 API | `POST /api/v0/kindergarten/load-csv` | 인증 없이 CSV 일괄 재적재 가능 |

### 후속 확인 필요

- `POST /user/restore`(탈퇴 복구) — 미사용 확인됐으나 폐기 전 기획 측 확인 권장
- `GET /kindergarten/basic/{id}` vs `main/{id}` 통합 여부 — `v1` 설계 시 프론트와 함께 재검토

전체 목록/상세는 구현 단계에서 도메인별 지시서(`docs/domains/*.md`)로 구체화한다.

### 구현 메모 — Redis 공유 + `flushDb()` 미호출

kindergarten 도메인은 DB가 아니라 Redis가 주 저장소다. 자바 서버는 기동마다 위 표의 `flushDb()` 버그로 같은 Redis의 리프레시 토큰까지 지운다. 자바 서버는 이번 스프린트에서 손대지 않되(위 부록), 신규 서버는 같은 Redis를 공유하면서도 로더를 **조건부 시드(키 없을 때만 적재)**로 구현해 `flushDb()`를 호출하지 않는다.

### 구현 메모 — 작업 단위는 유스케이스 슬라이스

도메인 하나(예: kindergarten 89파일, 8.2k LOC)를 통째로 AI 세션에 맡기면 컨텍스트가 넘쳐 품질이 무너진다. 그래서 도메인당 **선행 기반 태스크**(순수 도메인 모델 + persistence/cache 어댑터, 1회, 병렬 불가) 하나를 먼저 끝내고, 그 이후 **유스케이스 슬라이스**(엔드포인트 1~3개, 파일 6~12개)로 쪼개 병렬 진행한다. 이 패턴을 12개 도메인에 적용하면 도메인 기반 태스크 12개 + 유스케이스 태스크 35~40개, 총 45~50개 태스크가 나온다. 완료 판정 기준은 [`workflow.md`](../workflows/000-common.md) §5 참고.
