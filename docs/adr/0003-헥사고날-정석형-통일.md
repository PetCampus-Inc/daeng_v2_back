# 0003. 헥사고날 경계는 ArchUnit으로 강제, 전 도메인 정석형 통일

## 맥락

`daeng_v2_back`에는 이미 경계 테스트와 함께 두 가지 스타일의 예제가 있었다 — `owner`(정석형: 순수 도메인 + JPA 엔티티 분리 + 매퍼)와 `bookmark`(실용형: 더 단순한 구조). 도메인마다 AI 에이전트가 어떤 스타일을 쓸지 매번 새로 판단하게 둘지, 하나로 통일할지 결정이 필요했다.

## 검토한 후보

1. 도메인 성격에 따라 정석형/실용형을 혼용한다(기존 상태 유지).
2. 전 도메인을 정석형으로 통일하고, 헥사고날 경계 위반을 ArchUnit으로 예외 없이 강제한다.

## 결정

**후보 2 — 전 도메인 정석형 통일 + ArchUnit 강제.**

근거: 실용형과 혼재시키면 AI 에이전트가 도메인마다 다르게 판단해 일관성이 깨진다. 이미 `owner` 예제가 있으므로 이를 표준 템플릿으로 삼는 비용이 낮다.

## 결과

**표준 슬라이스 구조** (`owner` 예제 기준):

```
domain/<도메인>/
  domain/                       순수 도메인 모델 + VO (Spring/JPA 의존 금지 — ArchUnit 강제)
  application/
    port/input/<X>UseCase.kt    유스케이스 인터페이스, 유스케이스 1개당 1파일
    port/output/<X>Port.kt      아웃바운드 포트
    service/<X>Service.kt       유스케이스 구현
  adapter/
    inbound/web/<X>Controller.kt   유스케이스별로 컨트롤러도 분리 (병렬 작업 충돌 방지)
    outbound/persistence/           JPA 엔티티 · Repository · PersistenceAdapter · Mapper
```

kindergarten처럼 DB가 아니라 **Redis가 주 저장소인 도메인**은 `adapter/outbound/persistence/` 대신 `adapter/outbound/cache/`(Redis 어댑터)로 명명하되, 포트 인터페이스는 동일한 패턴(`LoadXPort`/`SaveXPort`)을 따른다.

**ArchUnit 규칙** (기 구축, 그대로 유지):
1. `application` → `adapter` 의존 금지
2. `application` → `jakarta.persistence` 의존 금지
3. `domain` → `application`/`adapter` 의존 금지
4. 순수 도메인 → `org.springframework.*`/`jakarta.persistence.*` 의존 금지

완료 판정 기준(ArchUnit/ktlint/골든 테스트)은 [`workflow.md`](../workflows/000-common.md) §5의 "완료 확인 기준 작성 가이드"에 흡수됐다.

**구현 메모 — 매핑 라이브러리는 도입하지 않음**: 레거시의 QueryDSL 커스텀 리포지토리 19개는 전부 레거시 `domain/repository/`에만 있고 v3(비-`@Deprecated`) 사용이 0건이었고, MapStruct도 의존성만 선언돼 있을 뿐 실제 `@Mapper` 사용이 0건이었다. 둘 다 신규 서버로 가져가지 않고, 위 슬라이스 구조의 매핑 계층은 수동 매퍼 클래스로 작성한다.
