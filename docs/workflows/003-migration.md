# 마이그레이션 작업 추가 절차

이 문서는 [`000-common.md`](000-common.md)의 공통 단계에 결합하는 추가 조건이다. 별도의 단계·작업 문서 양식을 만들지 않는다. 마이그레이션의 상세 요구사항·결정·검증 결과는 `docs/work/<JIRA-KEY>-<slug>.md`에 기록하고 Jira 본문에는 복제하지 않는다.

## 1단계에 추가할 확인 사항

- 이관 목적, 원본·대상, 포함·제외 범위, 완료 조건, 허용 호환성 범위를 확인한다.
- 레거시 구현, 실제 호출 클라이언트, 데이터 원본, 외부 연동, 운영 의존성을 근거로 확인한다. 근거 없이 미사용으로 판단하지 않는다.
- API·데이터·연동 인벤토리와 기존 ADR을 확인해 `KEEP`·`REDESIGN`·`DROP`·`DEFER` 판단과 미확인 항목을 기록한다.
- **기록:** 확인 결과를 작업 문서의 `작업 목표`, `작업 범위`, `작업 제외 범위`에 남긴다.

## 2단계에 추가할 계획·승인 조건

- 기존 계약 유지 또는 신규 버전, 전환 중 공존 방식, 호출 주체별 전환 순서를 결정한다.
- 데이터가 있으면 원본·대상 스키마, 변환 규칙, 정합성 기준, 실패 처리, 재실행 가능성을 결정한다.
- cutover·rollback 필요 여부, 실행 조건, 성공·중단 기준, 복구 방법, 운영 책임자를 결정한다. 필요 없으면 근거와 함께 명시한다.
- 사용자 승인은 이관 범위, 전환·rollback 설계, 검증 계획을 모두 포함해야 한다. 이 정보가 비어 있거나 승인되지 않았으면 구현·데이터 변경·외부 전환을 시작하지 않는다.
- **기록:** 공존 방식, 데이터 변환·정합성, 실패 처리·재실행, cutover·rollback, 운영 책임자와 승인 기록은 `방향 논의 및 결정 사항`에 남긴다. 계약 parity와 데이터 정합성의 통과 기준은 `완료 확인 기준`에 남긴다.

## 3단계에 추가할 구현 조건

- 확인된 계약과 데이터를 기준으로 구현한다. 확인되지 않은 레거시 동작을 임의로 재현하지 않는다.
- 공존 기간에는 이중 쓰기, 읽기 우선순위, 캐시 무효화, 권한 차이 등 해당 위험을 명시적으로 처리한다.
- secret을 작업 문서에 기록하지 않는다. 환경별 적용 순서와 책임 범위는 필요한 경우 `docs/inventory/operations.md`에 반영한다.
- 운영 환경 데이터 변경·cutover는 이 단계의 일반 구현에 포함하지 않는다. 별도로 승인된 운영 runbook 없이는 실행하지 않는다.
- **기록:** 구현 중 범위·계약·전환 설계가 바뀌면 `작업 범위` 또는 `방향 논의 및 결정 사항`을 먼저 갱신한다.

## 4단계에 추가할 검증 조건

- 계약 보존 대상은 요청·응답·상태 코드·오류 코드·권한 동작을 비교해 검증한다. `KEEP` API는 아래 **로컬 응답 대조**를 수행한다.
- 데이터 이관 대상은 row count, checksum, 샘플 비교 등 대상에 맞는 정합성 기준을 실행하고 결과를 기록한다.
- 재실행·실패 처리·rollback은 가능한 범위에서 검증한다. 검증하지 못한 항목과 제한은 명시한다.
- **기록:** 검증 방법, 통과 기준, 실제 결과와 제한은 `완료 확인 기준`에 남긴다.

### `KEEP` API 로컬 응답 대조

`KEEP`은 프론트가 이미 쓰는 계약을 그대로 유지해야 하는 판정이다([`api-migration.md`](../rules/api-migration.md) §2). 자동 golden 테스트는 없다 — 레거시는 다른 저장소이고 CI에서 띄울 수 없다. 대신 **로컬에서 사람이 대조하고 결과를 작업 문서에 남긴다.**

`REDESIGN` API는 이 절차의 대상이 아니다. 계약을 바꾸기로 한 판정이기 때문이다.

1. **레거시 응답 형태 확인** — `knockdog_server` 저장소에서 해당 컨트롤러 메서드와 응답 DTO, `common/response/Response.java`의 공통 응답 래퍼를 읽는다. 서버를 띄울 수 있으면 실제 응답 JSON을 뜨는 쪽이 정확하다.
2. **신규 응답 확인** — 로컬 기동 후 같은 요청을 보내 응답을 뜬다.

   ```bash
   docker compose --env-file .env.local -f docker-compose.local.yaml up -d
   set -a && source .env.local && set +a
   ./gradlew bootRun --args='--spring.profiles.active=local'
   ```

3. **아래 항목을 하나씩 대조한다.** 다르면 그대로 두지 말고, 프론트 저장소(`daeng_v2_front`)에서 **그 필드를 실제로 읽는지** 확인한 뒤 판단한다.

   | 대조 항목 | 확인 방법 |
   |---|---|
   | HTTP status code | 성공·실패 경로 각각 |
   | 공통 응답 래퍼(`Response<T>`) | 필드 구성, 성공 시 `code` 값, null 필드 생략 여부. `data` 안쪽 DTO와 그걸 감싸는 래퍼를 따로 본다 |
   | `data` 내부 필드 | 이름·타입·null/빈 배열 처리 |
   | 에러 코드 문자열 | 프론트가 분기하는 값이면 절대 변경 금지 |
   | 날짜 포맷·timezone | |
   | 정렬·페이징 | 기본 정렬, cursor/page 의미 |
   | 인증 실패 응답 | status와 `code` — 프론트 인터셉터가 여기서 토큰 갱신을 분기한다 |

4. **프론트 소비처 확인** — 차이를 발견하면 프론트에서 그 필드를 읽는 코드를 찾는다. `data`만 꺼내 쓰면 차이를 허용해도 되고, 래퍼 필드(`code` 등)로 분기하면 맞춰야 한다. **"안 쓸 것 같다"로 넘기지 않는다** — 실제로 `code !== 'SUCCESS'`로 분기하는 곳이 있다.
5. **기록** — 대조한 항목, 발견한 차이, 차이를 허용했다면 그 근거(프론트 소비처 확인 결과)를 작업 문서 `완료 확인 기준`에 남긴다. 대조하지 못한 항목은 제한으로 명시한다.

첫 사례는 [`KD3-258`](../work/KD3-258-user-social-auth.md)의 약관 동의 2개다 — 공통 응답 래퍼 차이를 발견하고 프론트 소비처를 확인해 허용으로 결론냈으며, 같은 과정에서 인증 실패 status 불일치(403 vs 401)를 잡았다.

## 5단계에 추가할 검토·문서화 조건

- 리뷰어는 원본·대상 범위, 계약 호환성, 데이터 정합성, 공존 위험, rollback 근거를 작업 문서와 diff에 대조한다.
- 실제 운영 전환 전에는 승인된 runbook, 책임자, 성공·중단 기준, 복구 방법이 준비됐는지 확인한다. 이는 PR·머지와 별개인 운영 절차다.
