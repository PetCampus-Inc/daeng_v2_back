# 마이그레이션 작업 절차

모든 레거시 기능·데이터·외부 연동의 이관 또는 전환 작업은 [`000-common.md`](000-common.md)의 **작업 유형 적용** 표에 따라 이 절차를 결합해 따른다. 이 파일은 공통 절차가 끝난 뒤 별도로 수행하는 순차 절차가 아니다. 사람과의 대화·탐색으로 구체화한 내용은 5단계에서 `docs/work/<JIRA-KEY>-<slug>.md`에 직접 기록하고, 이후 결정·구현·검증 결과를 계속 갱신한다. Jira 본문에는 복제하지 않는다.

## 대화 단계와 게이트

| 단계 | 다음 단계로 넘어갈 조건 |
|---|---|
| M1 원본·대상·완료 기준 | 이관 대상, 포함·제외 범위, 허용 호환성과 완료 기준이 확인됨 |
| M2 계약·데이터·운영 영향 조사 | 실제 호출 주체, 데이터 원본·대상, 외부 연동·운영 의존성과 미확인 항목이 기록됨 |
| M3 전환·공존·rollback 설계 | 변환·정합성 검증·실패 처리·재실행, cutover·rollback 방안이 결정됨 |
| M4 작업 문서·구현 계획 승인 | 사용자가 범위, 전환 설계, 검증 계획을 승인함 |
| M5 구현·정합성 검증 | 계약 parity, 데이터 정합성, 회귀 검증의 근거가 준비됨 |
| M6 PR 리뷰·전환 준비 | 리뷰 결과와 미검증 제한, 실제 전환 전 확인 항목이 정리됨 |

M1~M3의 필수 정보가 비어 있거나 M4 승인이 없으면 구현·데이터 변경·외부 전환을 시작하지 않는다.

5단계에서는 아래 **작업 문서 양식**을 `docs/work/<JIRA-KEY>-<slug>.md`로 복사해 사용한다. 이 파일의 절차와 양식이 마이그레이션 작업의 단일 기준이다.

## 1. 원본과 대상 범위 확인

- 사람과 대화해 이관 목적, 완료 조건, 허용되는 호환성 범위와 제외 범위를 확정한다.
- 레거시 구현, 실제 호출 클라이언트, 데이터 원본, 외부 연동, 운영 의존성을 확인한다. 근거 없이 미사용으로 판단하지 않는다.
- API·데이터·연동 인벤토리와 기존 ADR을 확인해 `KEEP`·`REDESIGN`·`DROP`·`DEFER` 판단을 따른다.

## 2. 전환 방향 결정

- 기존 계약을 유지할지, 신규 버전으로 설계할지와 전환 기간 중 공존 방식을 결정한다.
- 데이터가 있으면 원본·대상 스키마, 변환 규칙, 정합성 검증, 실패 처리, 재실행 가능성을 결정한다.
- 배포·cutover·rollback이 필요한지 판단하고, 필요한 경우 실행 조건과 복구 방법을 작업 문서에 남긴다.

## 3. 구현과 전환 준비

- 원본 분석으로 확인한 계약과 데이터를 기준으로 구현한다. 확인되지 않은 동작은 임의로 재현하지 않고 사람에게 확인한다.
- 기존·신규 경로가 함께 동작하는 기간에는 데이터 이중 쓰기, 읽기 우선순위, 캐시 무효화, 권한 차이 등 해당 위험을 명시적으로 처리한다.
- 운영 변경이 있으면 secret을 문서에 기록하지 않고, 환경별 적용 순서와 책임 범위를 운영 문서에 반영한다.

## 4. 검증과 전환 확인

- 계약 보존 대상은 요청·응답·상태 코드·오류 코드·권한 동작을 레거시와 비교해 검증한다.
- 데이터 이관 대상은 row count, checksum, 샘플 비교 등 대상에 맞는 정합성 검증 기준을 실행한다.
- 배포·전환·rollback 절차가 있으면 실제 적용 전 검토 가능한 수준으로 검증하고, 검증하지 못한 항목은 작업 문서에 제한 사항으로 남긴다.

## 5. 작업 문서 필수 반영 항목

- 이관 원본·대상·포함·제외 범위와 근거
- 계약 호환성, 데이터 변환, 공존·전환·rollback의 결정과 책임
- 실행한 parity·정합성·회귀 검증과 결과
- 갱신한 API, 데이터베이스, 연동, 운영, 아키텍처, ADR 문서 목록
