# 공통 작업 절차

이 문서는 Jira 티켓을 받아 PR·머지 준비까지 진행하는 **유일한 공통 순서**를 정의한다. 작업 성격에 따라 [`003-migration.md`](003-migration.md), [`005-new-feature.md`](005-new-feature.md) 등 유형별 workflow를 이 순서에 결합한다. 유형별 문서는 별도 순서를 만들지 않고, 각 공통 단계에서 추가로 확인·결정·검증할 조건만 정의한다.

Jira는 일정·상태·담당·우선순위·스프린트·상위 에픽을 관리한다. 상세 요구사항, 결정, 검증 결과의 단일 기준은 `docs/work/` 문서다. AI는 Jira를 기본 읽기 전용으로 사용하며, 브랜치를 생성·checkout·변경하지 않는다.

## 단계 한눈에 보기

각 공통 단계 안에서 실제로 밟는 순서다. 유형별 workflow는 이 순서를 바꾸지 않고 각 단계에 조건만 더한다.

| 공통 단계 | 순서 | 산출물 |
|---|---|---|
| 1. 작업 맥락·요구사항 구체화 | 브랜치 일치 확인 → 작업 유형 판정 → 요구사항 구체화 → 문서 영향 판정 | (사람과의 대화) |
| 2. 계획 승인·작업 문서 생성 | 대안 비교 → 사용자 승인 → 작업 문서 생성 | `docs/work/<JIRA-KEY>-<slug>.md` |
| 3. 구현 | 승인 범위 안에서 구현 → 연관 단위로 커밋 | 코드, 커밋 |
| 4. 검증 | 완료 확인 기준 대조 → 테스트·정적 검사 실행 → 미검증 항목 기록 | 검증 결과 |
| 5. 독립 리뷰·PR·문서 동기화 | 독립 리뷰 → 수정 반복 → PR 생성 → 문서 갱신 → 머지 준비 | PR, 갱신된 `docs/` |

## 유형별 workflow 결합 규칙

- 1단계에서 작업 유형을 판정한다. 한 티켓에 여러 성격이 있으면 해당 유형의 추가 조건을 모두 적용한다.
- 유형별 workflow는 아래 공통 단계의 번호를 그대로 사용한다. 공통 단계와 다른 순서를 지시하지 않는다.
- 여러 workflow의 조건이 충돌하면 더 엄격한 조건을 적용하고, 판단할 수 없으면 사람에게 묻는다.
- `001-current-status.md`, `002-continue-work.md`는 작업 유형이 아니라 읽기 전용 진입 절차다.
- `003`부터 `008`까지의 유형 문서는 이 결합 형식으로 정리돼 있다.
- `006-code-review.md`는 읽기 전용 리뷰 workflow다. 5단계에서 추가 독립 리뷰를 요구하지 않고, 발견 사항·제한·후속 작업을 정리해 종료한다. 사용자가 요청하거나 고위험 변경의 머지 게이트인 경우에만 별도 독립 리뷰를 수행한다.

## 1. 작업 맥락·요구사항 구체화

사람은 Jira에서 티켓과 작업 브랜치를 만든 뒤 AI에 Jira 키·제목과 작업 브랜치명(필수), 상위 에픽 키(선택)를 제공한다. AI는 현재 브랜치가 제공받은 브랜치와 일치하는지 확인한다. 일치하지 않거나 브랜치 정보가 없으면 알리고 중단한다.

사람과 대화하고 코드·문서를 탐색해 아래를 구체화한다. 불확실한 내용은 구현으로 추정하지 않는다.

문서 영향이 있는 작업은 [`docs/rules/documentation.md`](../rules/documentation.md)의 배치·갱신 기준을 읽어 적용 대상 문서를 판정한다.

- 배경과 사용자·운영상의 문제
- 작업 목표, 포함 범위, 제외 범위, 완료 확인 기준
- 관련 모듈, 실제 호출 주체, API·데이터·외부 연동·운영 영향
- 적용할 작업 유형과 유형별 미결 질문
- 작업 후 갱신 여부를 확인할 문서

## 2. 계획 승인·작업 문서 생성

1단계의 내용을 바탕으로 대안과 선택 이유, 구현 순서, 검증 방법, 위험과 제한을 사용자와 대화한다. 이 단계에서는 채팅과 읽기 전용 탐색만 수행하며, `docs/work/`를 포함한 파일·데이터·외부 시스템을 변경하지 않는다.

승인 전에 `미결 질문`을 함께 확인한다. **질문이 없는 것과 묻지 않은 것은 다르다** — 미결 질문이 비어 있으면 그 자체를 확인 대상으로 보고, 확인하지 않은 채 추정으로 넘어간 항목이 없는지 사용자와 함께 점검한다.

사용자가 계획을 승인한 직후, 구현을 시작하기 전에 1단계 내용과 승인 기록을 `docs/work/<JIRA-KEY>-<kebab-설명>.md`에 기록한다. 이 문서는 티켓 상세 정보의 단일 기준이며 커밋 대상이다. 아래 공통 양식을 사용하고, 적용한 유형별 workflow가 요구하는 하위 항목을 해당 섹션에 추가한다.

### 작업 문서 공통 양식

```markdown
> 생성: YYYY-MM-DD HH:MM · 최종 수정: YYYY-MM-DD HH:MM

# <JIRA-KEY> <작업 제목>

| 항목 | 값 |
|---|---|
| Jira | `<JIRA-KEY>` |
| 브랜치 | 사람이 생성해 제공한 작업 브랜치명 |
| 상위 에픽 | `<JIRA-EPIC-KEY>` 또는 해당 없음 |

## 현재 제어점

- 활성 workflow: `<예: 003-migration, 005-new-feature>`
- 현재 공통 단계: `<1~5>`
- 다음 결정 또는 전환 조건: `<무엇이 충족되어야 하는가>`

## 작업 목표

## 작업 범위

## 작업 제외 범위

## 방향 논의 및 결정 사항

### 확정 사항

### 미결 질문

### 사용자 승인 기록

## 완료 확인 기준

## 작업 후 확인 목록
```

`현재 제어점`은 Jira 상태를 복제하지 않는다. 현재 대화·작업이 어느 공통 단계에 있으며 다음에 어떤 결정을 해야 하는지를 기록한다. 단계 전환, 승인, 범위 변경 때만 갱신한다.

이 양식은 이 공통 절차를 적용한 뒤 새로 만드는 `work/` 문서의 기준이다. 이전에 완료한 문서는 historical record로 보존하며 양식에 맞추기 위해 소급 수정하지 않는다. 기존 미완료 작업을 이어갈 때도 문서 전체를 변환하지 않고, 현재 진행·결정·검증 결과를 기존 문서의 적절한 위치에 이어 기록한다.

## 3. 구현

승인된 작업 문서와 계획 범위 안에서 구현한다. 연관된 작업 단위로 커밋하고, 커밋 메시지는 [`git.md`](../rules/git.md)를 따른다. 구현 중 새 요구사항·설계 변경·영향 범위가 발견되면 코드를 먼저 확장하지 말고 작업 문서에 기록한 뒤 1단계 또는 2단계로 돌아가 사용자와 결정한다.

이 단계는 코드와 개발·검증 환경의 변경을 다룬다. 운영 환경 데이터 변경, cutover, 배포 전환은 유형별 workflow에서 별도 실행 승인을 요구하는 경우 그 절차를 따른다.

## 4. 검증

작업 문서의 완료 확인 기준을 실제 결과와 대조한다. 변경 위험에 맞는 테스트·정적 검사·통합 검증을 실행하고, API 계약·데이터 정합성·권한·문서·운영 영향도 함께 확인한다. 실행하지 못했거나 검증할 수 없었던 항목은 이유와 제한을 문서에 남긴다.

검증 결과가 목표나 승인 범위와 어긋나면 2단계 또는 3단계로 돌아간다.

## 5. 독립 리뷰·PR·문서 동기화

`006-code-review`를 제외한 workflow는 컨텍스트를 공유하지 않는 리뷰어에게 작업 문서 경로와 리뷰 대상 커밋 범위를 전달한다. 리뷰어는 작업 문서와 실제 diff를 대조해 누락, 범위 초과, 계획과 다른 구현을 확인한다. 발견된 문제는 성격에 따라 2단계(계획), 3단계(구현), 4단계(검증)로 되돌아간다. **리뷰가 제기한 문제가 전부 해소되거나, 이번 범위에서 다루지 않기로 한 항목이 작업 문서의 `작업 제외 범위`에 이유와 함께 기록될 때까지 반복한다.** 남겨두기로 한 지적을 기록 없이 넘기지 않는다.

PR을 만들기 전과 머지 직전에 작업 문서, PR 본문, 코드가 일치하는지 확인한다. [`documentation.md`](../rules/documentation.md)의 배치·갱신 기준으로 판정한 문서를 갱신하거나 확인하고, 결과와 근거를 작업 후 확인 목록에 남긴다. PR 템플릿에는 Jira와 작업 문서 경로를 연결한다. 현재는 작업 문서와 확인 목록의 존재·형식을 CI로 강제하지 않으므로, 리뷰어는 문서 영향 판정의 타당성·문서 내용·Notion API 명세 반영 여부를 실제 코드와 대조한다. 문서 갱신과 필수 검증이 끝난 뒤에만 머지를 준비한다.

AI는 선택한 workflow를 세션의 활성 workflow로 유지한다. 매 답변에 상태를 반복하지 않고 단계 전환, 승인 요청, 범위 이탈, 구현·PR 직전 검증에서만 현재 단계·확정 사항·미결 질문·다음 결정을 짧게 안내한다. 새 요청은 현재 범위 내 작업, 범위 변경, 별도 티켓으로 분류하며 후자의 둘은 사용자의 선택 없이 조용히 전환하지 않는다.
