# 공통 작업 절차

이 문서는 Jira 티켓을 받아서 머지까지 끝내는 전체 작업 절차를 정의한다. 특정 AI 도구나 플러그인에 의존하지 않는다 — 어떤 코딩 에이전트를 쓰든 이 절차를 그대로 따른다. 작업 성격에 따라 [`005-new-feature.md`](005-new-feature.md), [`003-migration.md`](003-migration.md), [`004-bug-fix.md`](004-bug-fix.md), [`006-code-review.md`](006-code-review.md), [`007-design-research.md`](007-design-research.md), [`008-documentation.md`](008-documentation.md)의 추가 절차를 결합해 따른다.

## 대화 진행 제어

AI는 선택한 workflow를 세션의 활성 workflow로 유지한다. 각 단계 안에서는 필요한 탐색과 대화를 자유롭게 수행하되, 아래 전환점에서만 현재 단계·확정 사항·미결 질문·다음 결정을 짧게 정리한다.

| 공통 단계 | 전환 조건 | AI가 해야 할 일 |
|---|---|---|
| C1 맥락·요구사항 구체화 | 작업 목표·범위·제외 범위·완료 기준을 설명할 수 있음 | 유형별 workflow를 판정하고 미결 질문을 제시 |
| C2 작업 문서·구현 계획 승인 | `work/` 문서 초안과 구현·검증 계획이 준비됨 | 사용자에게 승인 또는 수정 방향을 요청 |
| C3 구현 | 사용자가 C2 계획을 승인 | 승인 범위 안에서만 구현하고, 범위 변경 시 C1 또는 C2로 돌아감 |
| C4 검증 | 구현 범위가 완료됨 | 완료 기준, 문서·계약·데이터·운영 영향, 미검증 제한을 대조 |
| C5 리뷰·PR·머지 준비 | 검증 근거가 준비됨 | 작업 문서와 diff를 대조하고 리뷰·PR·문서 동기화 절차 진행 |

- 사용자의 새 요청은 현재 범위 내 작업, 범위 변경, 별도 티켓 중 하나로 분류한다. 범위 변경이나 별도 티켓이면 조용히 전환하지 않고 사용자의 선택을 받는다.
- C2 승인 전에는 파일·데이터·외부 시스템을 변경하지 않는다. C3 이후에도 승인된 범위를 넘는 변경은 다시 C2 승인을 받는다.
- 작업 문서에는 확정 사항, 미결 질문, 사용자 승인 기록을 남긴다. Jira 상태는 Jira에서만 관리한다.
- 매 답변에 상태 보고를 반복하지 않는다. 단계 전환, 승인 요청, 범위 이탈, 구현·PR 직전 검증에서만 체크포인트를 제시한다.

## 전체 흐름

| 단계 | 이름 | 산출물 |
|---|---|---|
| 1 | 티켓 수령 + 작업 브랜치 확인 | Jira 키·제목, 사용자가 만든 브랜치 |
| 2 | 작업 맥락 확인 | (사람과의 대화) |
| 3 | 작업 브랜치 검증 | 확인된 현재 브랜치 |
| 4 | 구현 방향 논의 | (사람과의 대화) |
| 5 | 작업 문서 작성 | `docs/work/<JIRA-KEY>-<kebab-설명>.md` |
| 6 | 구현 | 코드 |
| 7 | 커밋 | 커밋 (연관 작업 단위) |
| 8~9 | 리뷰 및 개선 | 리뷰 코멘트 반영 |
| 10 | PR 생성 | PR |
| 11 | PR 리뷰 및 수정 | 반영된 코드 |
| 12 | 문서 동기화 + 머지 | 최신화된 docs/*, 머지 |

## 1. 티켓 수령 + 작업 브랜치 확인

Jira는 일정·상태·담당·우선순위·스프린트·상위 에픽을 관리하는 도구다. 상세 요구사항, 결정, 검증 결과는 Jira 본문에 복제하지 않고 `docs/work/` 문서를 단일 기준으로 관리한다.

사람이 Jira에서 티켓과 작업 브랜치를 생성한 뒤 AI에 아래 정보를 제공한다.

| 항목 | 필수 여부 | 용도 |
|---|---|---|
| Jira 키·제목 | 필수 | 작업 문서 파일명과 작업 식별 |
| 작업 브랜치명 | 필수 | AI가 작업할 브랜치 확인 |
| 상위 에픽 키 | 선택 | 티켓 관계 추적 |

AI는 Jira를 기본 읽기 전용으로 사용하며, 본문·상태·댓글·담당자·라벨·스프린트를 수정하지 않는다. AI는 브랜치를 생성·checkout·변경하지 않는다.

## 2. 작업 맥락 확인

제목만 있는 티켓을 시작점으로 사람과 대화하고 코드·문서를 탐색해 아래 세 가지를 구체화한다. 확정한 내용과 미결 질문은 5번 작업 문서에 기록한다.

1. **배경/맥락**: 이 티켓이 왜 생겼는가. 관련 ADR(`docs/adr/`), 도메인 지시서(`docs/domains/`), 이전 대화/코멘트를 확인한다.
2. **작업 범위**: 생성/수정/삭제되어야 할 코드가 무엇인가. 파일·모듈 단위로 구체화한다.
3. **작업 후 확인 목록**: 완료 후 갱신해야 할 문서가 무엇인가. 작업 성격에 따라 다르다.

| 작업 성격 | 확인해야 할 문서 |
|---|---|
| 아키텍처/설계 변경 | `docs/adr/`, `docs/architecture/` |
| API 추가/변경 | Notion API 명세서 — 연동 방법은 [`docs/conventions/notion-api-spec-sync.md`](../conventions/notion-api-spec-sync.md) |
| 도메인 로직 변경 | `docs/domains/<domain>.md` |
| 이 문서들에 해당 없음 | 없음 — 생략 가능 |

### 작업 유형 적용

2번 작업 맥락 확인이 끝나기 전에 아래 표로 적용할 workflow를 판정한다. 하나의 티켓에 여러 작업 성격이 있으면 해당 workflow를 모두 적용한다. 판정 결과는 5번 `work/` 문서에 기록한다.

| 작업 유형 | 2번 작업 맥락 확인 | 4~5번 방향 논의·작업 문서 | 6번 구현 | 8~12번 리뷰·머지 |
|---|---|---|---|---|
| 신규 기능 | [`005-new-feature.md`](005-new-feature.md) §1 | `005-new-feature.md` §2 | `005-new-feature.md` §3 | `005-new-feature.md` §4~5 |
| 마이그레이션 | [`003-migration.md`](003-migration.md) §1 | `003-migration.md` §2 | `003-migration.md` §3 | `003-migration.md` §4~5 |
| 버그 수정 | [`004-bug-fix.md`](004-bug-fix.md) §1 | `004-bug-fix.md` §2 | `004-bug-fix.md` §3 | `004-bug-fix.md` §4~5 |
| 코드 리뷰 | [`006-code-review.md`](006-code-review.md) §1 | `006-code-review.md` §2 | `006-code-review.md` §3 | `006-code-review.md` §4~5 |
| 설계·조사 | [`007-design-research.md`](007-design-research.md) §1 | `007-design-research.md` §2 | `007-design-research.md` §3 | `007-design-research.md` §4~5 |
| 문서화 | [`008-documentation.md`](008-documentation.md) §1 | `008-documentation.md` §2 | `008-documentation.md` §3 | `008-documentation.md` §4~5 |

이 표가 workflow 적용 순서의 기준이다. 유형별 workflow를 공통 절차가 끝난 뒤 별도로 수행하지 않는다.

불확실한 부분은 사람에게 직접 묻는다. 짐작하지 않는다.

## 3. 작업 브랜치 검증

사람이 제공한 작업 브랜치와 현재 브랜치가 일치하는지 확인한다. 일치하지 않거나 브랜치가 제공되지 않으면 사람에게 알리고 중단한다. AI는 편의를 위해 다른 브랜치로 이동하거나 새 브랜치를 만들지 않는다.

## 4. 구현 방향 논의

2번에서 구체화한 범위를 실제로 어떻게 구현할지 논의한다. 여러 방법론 중 선택이 필요하거나 트레이드오프가 있는 지점을 짚는다. 결론이 아니라 "무엇을 검토했고 왜 배제했는지"까지 남긴다 — 이 논의 내용이 5번 문서의 근거가 된다.

## 5. 작업 문서 작성

4번 논의를 바탕으로 **하나의 문서**로 정리한다. 이 문서는 Jira 본문을 대체하는 티켓 상세 정보의 단일 기준이다. 2번의 작업 유형 적용 표에서 판정한 workflow의 **작업 문서 양식**을 `docs/work/<JIRA-KEY>-<kebab-설명>.md`로 복사해 시작한다. 두 유형이 모두 적용되면 한 양식을 기준으로 다른 양식의 유형별 하위 항목을 합친다. 이 문서는 커밋 대상이다.

H1 아래에 다음 추적 정보를 먼저 기록한다.

| 항목 | 값 |
|---|---|
| Jira | `<JIRA-KEY>` |
| 브랜치 | 사람이 생성해 제공한 작업 브랜치명 |
| 상위 에픽 | `<JIRA-EPIC-KEY>` 또는 해당 없음 |

**필수 섹션 (이 순서, 이 이름 그대로):**

| 섹션 | 내용 |
|---|---|
| 작업 목표 | 이 티켓이 끝나면 무엇이 달성되는가 (1~2문장) |
| 작업 범위 | 생성/수정/삭제될 파일·모듈 (2번 분석 결과 반영) |
| 작업 제외 범위 | 이번에 하지 않는 것 — 왜 제외했는지 포함 |
| 방향 논의 및 결정 사항 | 4번에서 검토한 대안들과 최종 선택, 그 이유 |
| 완료 확인 기준 | 이 작업이 끝났다고 판단할 구체적 기준 (아래 참고) |
| 작업 후 확인 목록 | 2번 표에서 확인된, 갱신해야 할 문서 목록 |

**완료 확인 기준 작성 가이드**: 작업 성격에 맞는 검증 방법을 구체적으로 명시한다. 예:
- 헥사고날 경계를 다루는 백엔드 작업: ArchUnit 통과, ktlint 통과, (기존 응답을 유지해야 하면) 골든 테스트로 레거시와 응답 JSON 100% 일치 확인
- 그 외 작업: 테스트 명령어와 통과 기준을 명시

이 문서는 8번 리뷰 단계에서 컨텍스트 없는 리뷰어에게 그대로 전달된다. 리뷰어가 이 문서만 보고 "무엇을, 왜, 어디까지" 작업했는지 알 수 있어야 한다.

## 6. 구현

5번 문서를 기반으로 구현한다. 문서에 없는 범위로 확장하지 않는다(YAGNI). 계획과 다르게 가야 할 이유가 생기면, 코드를 먼저 바꾸지 말고 5번 문서를 먼저 갱신한다.

## 7. 커밋

연관된 작업 단위로 나누어 커밋한다. 커밋 메시지 형식은 [`git.md`](git.md)를 따른다. 하나의 커밋에 서로 무관한 변경을 섞지 않는다.

## 8. 리뷰

새로운 세션(컨텍스트를 공유하지 않는 리뷰어)에게 리뷰를 맡긴다. 리뷰어에게 반드시 전달할 것:
- 5번 작업 문서 경로 — "요구사항과 배경은 이 문서를 읽어라"
- 리뷰 대상 커밋 범위 (base/head)

리뷰어는 작업 문서와 실제 diff를 대조해 다음을 확인한다: 계획에 있는데 빠진 것, 계획에 없는데 추가된 것, 계획과 다르게 구현된 것. 필요하면 리뷰어가 직접 코드베이스를 더 탐색할 수 있어야 한다.

## 9. 개선 반복

리뷰에서 나온 문제를 수정하고, 더 이상 고칠 부분이 없다고 판단될 때까지 8~9번을 반복한다. 리뷰가 지적한 문제를 "이번 범위 아님"으로 넘기려면, 5번 작업 문서의 "작업 제외 범위"에 이유와 함께 명시적으로 추가한다.

## 10. PR 생성

[`git.md`](git.md)의 PR 본문 템플릿을 따른다. 5번 작업 문서의 "작업 목표"/"작업 범위"를 PR의 Summary/Notes에 반영한다.

## 11. PR 리뷰 및 수정

사람 리뷰어와 AI 리뷰 도구의 코멘트를 반영한다. 반영 후에도 8~9번과 동일하게, 남겨두기로 한 지적은 이유와 함께 기록한다(PR 코멘트 답글 또는 5번 문서 갱신).

## 12. 문서 동기화 + 머지

머지 직전, 최종 PR 내용을 기준으로 아래를 갱신한다:
- 5번 문서의 "작업 후 확인 목록"에 있는 문서들 (`docs/adr/`, `docs/domains/*.md` 등)
- 티켓에서 도메인 경계·불변식·API/데이터/권한 제약·이관 상태를 확정하거나 변경했다면, `work/` 문서에 기록하는 것과 별도로 해당 `docs/domains/<domain>.md`도 갱신
- API를 추가/변경했다면 [`docs/conventions/notion-api-spec-sync.md`](../conventions/notion-api-spec-sync.md) 규칙에 따라 Notion API 명세서 페이지를 생성/수정
- PR 본문이 최종 코드와 어긋나 있으면 함께 갱신

문서 갱신까지 끝난 뒤에만 머지한다. "머지 후 문서화"는 하지 않는다 — 머지 시점의 코드와 문서가 항상 일치해야 한다.
