# 버그 수정 작업 추가 절차

이 문서는 [`000-common.md`](000-common.md)의 공통 단계에 결합하는 추가 조건이다. 별도의 단계·작업 문서 양식을 만들지 않는다. 버그 수정의 상세 요구사항·결정·검증 결과는 `docs/work/<JIRA-KEY>-<slug>.md`에 기록하고 Jira 본문에는 복제하지 않는다. 증상을 없애는 것만으로 완료로 판단하지 않으며, 재현 가능한 근거와 근본 원인, 회귀 방지 검증을 남긴다.

## 1단계에 추가할 확인 사항

- 기대 결과와 실제 결과, 재현 절차, 발생 환경·입력·빈도를 확인한다. 재현하지 못한 경우 그 사실과 제한을 기록한다.
- 사용자, 데이터, API 계약, 보안, 운영에 미치는 영향을 확인해 우선순위를 판단한다.
- 로그·메트릭·코드·테스트 등 근거로 추정 원인과 확인된 사실을 구분한다.
- **기록:** 기대·실제 결과와 재현 절차는 `작업 목표`와 `작업 범위`에, 영향 범위와 확인된 원인·가설은 `작업 범위`와 `방향 논의 및 결정 사항`에 남긴다.

## 2단계에 추가할 계획·승인 조건

- 증상 완화와 근본 원인 해결 중 무엇을 하는지, 범위와 제외 범위를 사용자와 확정한다.
- 데이터 보정, 계약 변경, feature flag, 배포·rollback이 필요하면 관련 workflow도 함께 적용한다.
- 재발을 막을 자동 테스트 또는 관찰성 보강 방법을 결정한다.
- 사용자 승인은 수정 범위, 근본 원인 또는 검증할 가설, 회귀 방지 방법을 포함해야 한다.
- **기록:** 수정·제외 범위와 대안·선택 이유, 근본 원인 또는 가설, 재발 방지 방법과 승인 기록은 `방향 논의 및 결정 사항`에 남긴다. 재현·회귀 검증의 통과 기준은 `완료 확인 기준`에 남긴다.

## 3단계에 추가할 구현 조건

- 확인한 원인을 해결하는 최소 범위로 수정한다. 재현되지 않은 가설을 사실처럼 구현하지 않는다.
- 테스트가 기존 결함을 실패로 재현하고 수정 후 통과하는지 확인한다. 불가능하면 이유와 대체 검증을 작업 문서에 남긴다.
- **기록:** 구현 중 원인·범위·가설이 바뀌면 `작업 범위` 또는 `방향 논의 및 결정 사항`을 먼저 갱신한다.

## 4단계에 추가할 검증 조건

- 재현 절차, 관련 회귀 경로, 인가·입력·오류 경로를 위험도에 맞게 검증한다.
- 수정 전후 재현이 불가능하면 대체 검증과 그 제한을 명시한다.
- **기록:** 검증 방법, 통과 기준, 실제 결과와 알려진 제한은 `완료 확인 기준`에 남긴다.

## 5단계에 추가할 검토·문서화 조건

- 리뷰어는 기대·실제 결과, 근본 원인 근거, 수정 범위, 회귀 방지 검증과 제한을 작업 문서와 diff에 대조한다.
- 사용자 영향이나 운영 대응이 바뀌면 `documentation.md`의 배치·갱신 기준을 적용한다.
