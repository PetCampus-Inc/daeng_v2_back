# 버그 수정 작업 절차

모든 버그 수정은 [`000-common.md`](000-common.md)의 작업 유형 적용 표에 따라 이 절차를 결합해 따른다. 증상을 없애는 것만으로 완료로 판단하지 않으며, 재현 가능한 근거와 근본 원인, 회귀 방지 검증을 남긴다.

## 대화 단계와 게이트

| 단계 | 다음 단계로 넘어갈 조건 |
|---|---|
| B1 증상·영향·근거 확인 | 기대·실제 결과, 재현 가능 여부, 영향 범위와 확인된 사실이 구분됨 |
| B2 수정·검증 계획 승인 | 수정 범위, 근본 원인 또는 검증할 가설, 회귀 방지 방법을 사용자가 확인함 |
| B3 구현·회귀 검증 | 수정 전후 재현 또는 대체 검증의 근거가 준비됨 |
| B4 리뷰·완료 판단 | 사용자 영향과 미검증 제한이 정리됨 |

## 1. 증상과 영향 범위 확인

- 기대 결과와 실제 결과, 재현 절차, 발생 환경·입력·빈도를 확인한다. 재현하지 못한 경우 그 사실과 제한을 기록한다.
- 사용자, 데이터, API 계약, 보안, 운영에 미치는 영향을 확인해 우선순위를 판단한다.
- 로그·메트릭·코드·테스트 등 근거로 추정 원인과 확인된 사실을 구분한다.

## 2. 수정 방향 결정

- 증상 완화와 근본 원인 해결 중 무엇을 하는지, 범위와 제외 범위를 사람과 확정한다.
- 데이터 보정, 계약 변경, feature flag, 배포·rollback이 필요하면 관련 workflow도 함께 적용한다.
- 재발을 막을 자동 테스트 또는 관찰성 보강 방법을 결정한다.

## 3. 구현

- 확인한 원인을 해결하는 최소 범위로 수정한다. 재현되지 않은 가설을 사실처럼 구현하지 않는다.
- 테스트가 기존 결함을 실패로 재현하고 수정 후 통과하는지 확인한다. 불가능하면 이유와 대체 검증을 작업 문서에 남긴다.

## 4. 검증과 문서화

- 재현 절차, 관련 회귀 경로, 인가·입력·오류 경로를 위험도에 맞게 검증한다.
- 사용자 영향이나 운영 대응이 바뀌면 해당 도메인·API·운영 문서를 갱신한다.

## 5. 작업 문서 필수 반영 항목

- 기대/실제 결과, 재현 절차와 영향 범위
- 근본 원인과 이를 뒷받침하는 근거, 불확실성
- 수정·제외 범위와 재발 방지 방법
- 실행한 재현·회귀 검증과 결과, 알려진 제한
