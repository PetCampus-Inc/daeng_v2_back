# API 인벤토리

이 문서는 레거시 서버에서 신규 서버로 이관할 API의 현재 상태와 판정을 관리한다. 상세 구현 지시서는 도메인 문서(`docs/domains/*.md`)나 티켓별 작업 문서(`docs/work/*.md`)에 둔다.

## 1. 판정 기준

| 판정 | 의미 |
|---|---|
| `KEEP` | 프론트/앱이 실제 사용 중이고 기존 `v0` 계약을 유지해야 하는 API |
| `REDESIGN` | 기능은 필요하지만 경로, 요청/응답, 권한, DB 구조 등을 재설계하거나 보강할 API. 계약 변경은 `v1`로 추가하고, 계약을 유지한 권한/프로필 보강은 `v0`에서 처리 |
| `DROP` | 미사용, 중복, 위험, 운영 가치가 낮아 신규 서버로 이관하지 않을 API |
| `DEFER` | 사용 여부나 정책 판단이 아직 불확실해 후속 확인이 필요한 API |

## 2. 이관 진척

`판정`이 "무엇을 할 것인가"라면 `이관 진척`은 "어디까지 했는가"다. 둘을 한 열에 섞지 않는다.

| 값 | 의미 |
|---|---|
| `완료` | 신규 서버에 구현되고 검증까지 끝난 API. **프론트 전환·컷오버는 별개다** — `v0+v1` 행의 `완료`는 v1이 구현됐다는 뜻이고, v0는 컷오버까지 레거시가 계속 제공한다 |
| `진행중` | 착수했으나 구현 또는 검증이 남은 API |
| `미착수` | 아직 손대지 않은 API. `DEFER`도 판정이 확정되면 이관 대상이 될 수 있으므로 여기 둔다 |
| `해당없음` | `DROP` 판정이라 신규 서버로 가져가지 않는 API |

`완료`는 실제 코드와 검증 결과가 있을 때만 적는다. 어느 작업에서 처리했는지는 그 행의 `후속 확인`에 `work/` 링크로 남긴다.

## 3. 작성 규칙

- 프론트/앱 호출 여부, 운영 사용 여부, 보안 위험 등 근거 없이 판정하지 않는다.
- 계약 유지가 필요한 `KEEP` API는 [`docs/rules/api-migration.md`](../rules/api-migration.md)의 계약 보존 기준을 따른다.
- 명백한 보안 버그나 폐기 확정 API는 parity 대상에서 제외하고, 제외 근거를 남긴다.
- 상세 request/response 명세는 구현 직전에 도메인 문서나 계획 문서에서 구체화한다.
- 레거시·프론트는 계속 변경되므로, 재추출할 때마다 4절에 기준 커밋 SHA와 날짜를 갱신한다. SHA 없이 갱신하면 다음 사람이 드리프트 범위를 알 수 없다.
